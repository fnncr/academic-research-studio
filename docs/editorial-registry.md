# Реестр редакторских критериев (P0)

Машиночитаемый снимок: [editorial-criteria.v1.json](../backend/app/data/editorial-criteria.v1.json), версия `1.0.0`, формат `schema_version: "1"`. Источник — [editorial-criteria.md](editorial-criteria.md). Строгие Pydantic-модели и загрузчик находятся в [editorial_registry.py](../backend/app/editorial_registry.py).

В спецификации исправлено только лишнее `33.` перед сигналами пункта 32. Все 34 названия, сигналы, рекомендации и исключения перенесены дословно; сохранены общие правила оценки и пять приоритетов. Форматирование списка не входит в значения JSON. Реестр не выполняет проверку документов и не подключён к API загрузки.

## Поля и валидация

Корневые обязательные поля: `schema_version`, `registry_version`, `source`, `source_sha256`, `evaluation_rules`, `priorities`, `criteria`. SHA-256 относится к байтам UTF-8 исходной спецификации и позволяет обнаружить изменение источника; содержательное соответствие дополнительно проверяют тесты.

У каждого критерия обязательны `id`, `name`, `description`, `description_status`, `signals`, `review_action`, `exceptions`. `signals`, `review_action`, `exceptions` — строки исходных формулировок, без разделения примеров на отдельные условия. ID — строка с ведущим нулём. Допускается ровно 34 элемента, строго 01–34, без повторов. Неизвестные поля, неправильные типы, пустые/пробельные строки и неподдерживаемая версия схемы отклоняются; преобразования числа в строку нет. Загрузчик также отклоняет повторяющиеся JSON-ключи и нестандартные NaN/Infinity.

`description` обязательно присутствует, но имеет `null`, если `description_status` равно `missing_in_source`. Для `provided` требуется непустой текст. В текущем источнике отдельные описания отсутствуют во всех 34 пунктах, поэтому все они помечены `missing_in_source`. Это документированный пробел, не пустая строка, не автоматически сгенерированное описание и не утверждение о содержательной завершённости P0. Подробности — в [реестре неоднозначностей](editorial-ambiguities.md).

Условия применимости, пороги частот, required_inputs и алгоритмы в JSON не добавлены: это не согласованные поля исходной спецификации. Предлагаемые методы в архитектуре не превращены в нормативные правила P0. Версия всего набора относится ко всем 34 критериям; индивидуальные версии критериев пока не нужны.

## Проверка и использование

Из корня репозитория:

```bash
(cd backend && ../.venv/bin/python -m app.editorial_registry)
(cd backend && ../.venv/bin/python -m pytest -q tests/test_editorial_registry.py)
(cd backend && ../.venv/bin/python -m pytest -q)
(cd frontend && npm test && npm run build)
```

`load_registry()` возвращает `EditorialRegistry`; путь по умолчанию вычисляется от модуля и не зависит от текущего каталога. Можно передать `Path` к другому JSON для проверки схемы. Загрузчик валидирует структуру, но не делает сетевых запросов и не сверяет произвольный JSON с Markdown. Сверка с исходной спецификацией выполняется тестом `test_registry_matches_entire_specification`: число и порядок заголовков, точные поля, отсутствие неперенесённых строк, правила, приоритеты и SHA-256. CLI выводит число критериев и отсутствующих описаний.

## Правила изменения версии

1. Сначала согласовать изменение исходной спецификации и явно описать его в PR. Не заполнять неизвестное значение догадкой и не считать исправление форматирования новым условием проверки.
2. Выпустить новый снимок JSON с новой `registry_version`; существующий выпущенный снимок не переписывать. Версия в имени следующего файла должна однозначно обозначать снимок (например, `editorial-criteria.v1.0.1.json`). Обновить `REGISTRY_PATH` и тест выбранной версии явно.
3. Patch — исправление технического представления; minor — согласованное описание без изменения смысла; major — изменение нормативного смысла/набора критериев. При изменении структуры отдельно поднять `schema_version` и реализовать поддержку/отказ загрузчика.
4. Обновить `source_sha256` и проверку соответствия нового снимка текущему Markdown. Старые снимки хранить для воспроизводимости; при необходимости проверки старой версии брать соответствующую ревизию Markdown из Git.
5. Просмотреть diff всех текстовых полей и запустить тесты. SHA-256 не заменяет содержательный review.

Исходное условие roadmap «все обязательные поля непустые» для отдельных description не может быть выполнено без новых согласованных формулировок. Техническая поставка P0 готовит строгий реестр с явным отсутствием данных; содержательная приёмка описаний остаётся открытой. P1–P10 этим изменением не реализуются.
