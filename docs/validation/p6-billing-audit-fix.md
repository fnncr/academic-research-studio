# P6: независимая проверка финансового контракта

Основание: `main` `99ef8b9`, 4 ноября 2026 года. Только синтетический
`httpx.MockTransport`; реальных запросов и счетов провайдера не было.

## Подтверждённые дефекты

**A01 — Critical, неполная проверка usage.** Адаптер игнорировал неизвестные
категории верхнего уровня usage, несогласованный total_tokens и cached_tokens
в детализации выходных токенов. Такие ответы могли завершаться успешным
списанием по неполному контракту. Отсутствующий usage и повреждённая детализация
удерживали резерв, но не блокировали следующие задания проекта.

Пять добавленных вариантов в `test_p6_faults.py` до исправления упали, исходные
пять прошли. Теперь обязательные prompt/completion/total проверяются как целые
неотрицательные числа с точной суммой; категории и их расположение разрешены
явно. Неизвестное поле отклоняется, даже если его значение нулевое. Документированные
nullable details допускаются; при отсутствии cached_tokens весь вход считается
по полной цене. Ненулевые audio/reasoning/prediction не поддерживаются.
Неопределённый финансовый контракт вызывает существующий UnconfirmedBilling:
резерв сохраняется, проект blocked, второе задание не отправляется.

**A02 — Medium, несовпадающие границы учёта.** `_settle` имел жёсткий предел
1 000 000 входных токенов при объявленной границе контекста 1 047 576.
Ответ внутри согласованной котировки мог оставаться ambiguous после отката
транзакции. Проверка теперь использует именно сохранённые границы котировки.
Резерв и тариф не увеличены. Контрактный тест учитывает 1 000 001 входной токен;
это проверка учёта, не утверждение, что такой контекст возможен с текущим
лимитом сериализованного запроса 128 000 байт.

## Проверка

`test_p6_faults.py`, `test_openai_gateway.py`, `test_p6_audit.py`: **35 passed**.
Свойства денежной арифметики проверены на 606 комбинациях, включая края, для
выходных лимитов 256/2000/8000: целочисленное округление вверх, монотонность
скидки кеша и cost <= reserve. Новый runtime-пакет не нужен.

Операционный компромисс: неизвестное расширение usage потребует проверки
владельцем, даже если впоследствии окажется бесплатным. Это сохраняет действующую
политику отказа при неподтверждённой тарификации. Сетевой таймаут без ответа
остаётся ambiguous с удержанным резервом; он сам по себе не доказывает смену
тарифа. Уже отправленные конкурентные вызовы невозможно отозвать задним числом.
Блокировка относится к проекту; при общей проблеме провайдера оператор должен
отключить approval и остановить workers для всех проектов по recovery runbook.

Проверка usage не обнаруживает незаявленное изменение цены при тех же счётчиках.
Перед включением нужны повторная проверка тарифов и согласие владельца.
Миграции, протокол согласия, UUID, запрет повторной отправки, ручной редактор
и схема Proposal не меняются.
